## 1. [model research] Whether hourly temperature-blindness and the daily/hourly feature mismatch should be reconciled at all

The daily grade and hourly badges answer genuinely different questions over different feature sets (research-report.md §8). Before any code changes to either formula, a separate, bounded round should decide: should the hourly view gain a temperature/sky signal, should the daily view's score-driving factors be made visible hour-by-hour, or should the two surfaces be explicitly documented as answering different questions (and the UI adjusted only to say so)? This is a product decision, not something this research round can resolve, and it has real impact on scores/rankings if the daily formula is the one changed — any change to `scoreSiteDay`, `getWindowState`, or their thresholds must be scoped as its own issue with an explicit before/after impact analysis on scores, Top-sites rankings, and Route Planner recommendations, per the project's own Free/Pro-gating-adjacent "shared forecast/scoring input" caution and this ticket's own scope limits.

## 2. [copy proposal] Make the daily score tooltip match what the formula actually computes

`ForecastTable.jsx:379-386`'s hover tooltip shows `Base/Wind/Rain = Points → Class` but silently omits `gustPen`, `shelterBonus`, and `pleasantness` (sky/cold-wind/wintry) — all three are real, sometimes decisive, contributors (confirmed in the real Oct-28 breakdown, research-report.md §4a/§9). A grounded copy fix would extend the tooltip string to include these terms using the same already-computed `r.*` fields the component already has in scope (`r.gustPen` exists on the row per `useForecast.js:184`; `shelterBonus`/`pleasantness` are not currently exposed on the row and would need to be added to the object `useForecast.js:176-188` returns before a tooltip could show them — that specific field-exposure change is itself small and additive, but is still a code change and is out of this research round's authorized scope; flagged here as the concrete next step, not performed).

## 3. [copy proposal] Make the hourly best-window label state its own limits

The "Best window 00–21" phrasing (`HourlyForecastModal.jsx:355`) reads as "calm the whole time", but by construction it only ever checked 8 of 24 hours and cannot see anything between two displayed samples (research-report.md §6d, §8). A grounded copy change would qualify the label (e.g. an IS/EN footnote "based on 3-hour samples" near the best-window line, or near each badge) so the claim matches what was actually evaluated. This is a translation-string-and-JSX change only; no logic change, no new dependency. Not performed in this round (instruction-file/i18n changes are out of scope here).

## 4. [verified display gap, product intent UNKNOWN — report, not fix] `ForecastTable.jsx`'s gust display gate (`>=15 m/s`) can hide a scoring-relevant gust value

> **Relabelled 2026-10-26 (R3):** this item was originally filed as "[verified bug]". That overstated it: the gate's existence and effect are verified, but whether a `>=15 m/s` cutoff is a *defect* (as opposed to a deliberate "don't clutter the row with every minor gust" decision) is a product-intent question with no documentation either way — **intent UNKNOWN**. Relabelled to "verified display gap, product intent UNKNOWN". The numeric band is also corrected per R1.

Confirmed by source + real execution (research-report.md §6a, §9): a gust in the roughly ~~11.1–14.9 m/s~~ **corrected: ~8.0–14.9 m/s for most raw weather codes, ~11.1–14.9 m/s specifically for clear-sky codes (0/1)** range (for the owner's own Oct-28 wind/temp baseline) is sufficient to flip the daily grade from "Fair" to "Bad" via `gustPenaltyPoints`, yet `ForecastTable.jsx:525-527` never displays `windGust` below 15 m/s, independent of the separate `gustWarn`/`gustHigh` (20/24) hazard thresholds in `src/config/hazards.js`. This is a real, reproducible display gap (the number that can decide the grade is invisible exactly in the range where it matters most for a low-wind, cold-sensitive day), not a hypothesis about the specific screenshots, and not itself evidence that the current threshold is wrong. A scoped follow-up could lower the display gate, or show gust whenever `gustPen > 0` regardless of its absolute value — either is a UI-only change but should be proposed as its own ticket with its own before/after screenshots and an explicit product decision on intent, since it changes what information is shown on every forecast row, not just this scenario.

A related, smaller rule-gap worth citing in that same follow-up ticket (research-report.md §9, R3): the hourly view's own "Good" threshold (`gust<=15`) and the daily winter formula's gustiness threshold (`gust-wind>=2.9`) disagree even within a single calm-looking reading — `wind=5, gust=8` is hourly "Good" but already costs 2 points on the daily score (`gustPenaltyPoints(8,5,"winter")=2`, confirmed by real execution). Any future UI change to surface gust more often should account for this, not just the `>=15` display gate.

## 5. [verified bug — report, not fix] `NaN` handling disagreement between `rainPenaltyPoints` and `getPrecipTimingMultiplier`

Confirmed by real execution (research-report.md §6c): the two functions use different guards against non-finite input, so a `NaN` rain value is computed one way by one function and effectively zeroed by the other's stricter check before the product is taken. Under normal Open-Meteo responses this is not user-visible (the provider is not expected to return `NaN`), but it is a genuine internal inconsistency worth a small, isolated hardening fix in a future ticket scoped to `scoring.js`'s own non-finite-input handling — not proposed as part of this research round, and not something to fix inside a documentation/research ticket per the project's own scope discipline.
