## Binding Jonesy D1–D5 (verbatim)

**D1 — Note rule for the routeRisk text lines (RoutePlannerCard).** `🚧 routeRiskAffectsDecision` (rendered whenever `routeRisk === "HIGH"`, also in preview) and `🚐 routeRiskLabel: …` (non-preview, non-LOW) sit in the verdict block, outside the alternatives list, and can be the only own indicator on screen (for example decision "stay" with no alternatives). Count them as own indicators. Rule: the card renders exactly one note if **any** own site or routeRisk indicator is rendered anywhere in the card; place it adjacent to the alternatives section when that section renders an indicator, otherwise adjacent to the routeRisk lines. Tests: HIGH-only with no alternatives shows one note; no indicator shows none; preview and full each show exactly one.

**D2 — Unique ids.** The note's `aria-describedby` target and every inline-expand `aria-controls` target must use per-instance ids (`useId`), not static strings. The card's note and the details modal's note (portal) can be mounted at the same time, and several rows each carry an expand control, so static ids would collide. Test: two hosts mounted together produce distinct ids and each link's description resolves to its own text.

**D3 — Aggregate-flag reasons use the flag's own data.** `hasHighWarning`/`hasWarning` are computed in `relocationEngine` over the candidate's `windowDaysExplained` (the engine window, `days = effectiveWindowDays`), and `useRoutePlanner` hands `candidate.windowDays` to the UI sliced to the same count. Derive reasons from that same `x.windowDays` array, with no extra or different slicing, and compute the displayed severity from the same data so label and reasons cannot disagree. CC must confirm in the pre-edit audit that `pickExplainDay` keeps `warnings` on each day; if a row has the flag but no per-day warnings, show severity and the existing route text only (no invented reason), and add a test for that case.

**D5 — ForecastTable placement detail.** The new line is a separate element inside the weather-text cell, rendered after (not inside) the existing summary IIFE, so the `summaryTextKey` early return and the precipitation caption logic are untouched.
