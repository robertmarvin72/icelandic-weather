## 1. Universal sharing — `weatherVoiceSharePolicy.js`'s disposition (explicit, per Jonesy's note)

**The unsupported-language rejection is retained exactly as before** — verified by test (`weatherVoiceSharePolicy.test.js`'s "an unsupported language is rejected even for an otherwise-eligible episode — retained exactly as before" covering `fr`, empty string, `undefined`, and case-sensitivity `IS`/`EN`).

**No hourly data dependency and no private-site flag were added** — confirmed by diff: `useForecast.js` is untouched (again), and `weatherVoiceShareSnapshot.js`'s `siteName` logic is byte-identical to Revision 1 (straight from `site.name`, no new filtering branch).

Severity and mood are confirmed never consulted (same eligibility result at severity 0 and severity 3).

## 2. Truthful localized daily context — fixed (Ripley Round 1 finding #1)

**Root cause confirmed:** `buildDailyContextLabel` called `Intl.DateTimeFormat("is-IS", {weekday:"long",...})`, and the real browser's `is-IS` locale weekday data was incomplete, silently falling back to an **English** weekday name ("Saturday") inside an Icelandic export — a genuine locale-data gap, not a logic bug in this module.

**Fix:** `formatShareDate(dateString, lang)` is now fully deterministic and Intl-independent — IS renders `dd.mm.yyyy` (e.g. `13.09.2026`), EN renders `D Mon YYYY` (e.g. `13 Sep 2026`), both **always including the year** (a persistent, dated artifact needs one). Verified by test that the IS output contains no Latin letters at all (`not.toMatch(/[a-zA-Z]/)`) — the exact shape of the original bug. `buildDailyContextLabel` now also explicitly labels the forecast as daily and the temperature as the day's high via two new i18n keys (`weatherVoiceShareDailyForecastLabel` = "Daily forecast"/"Dagsspá", `weatherVoiceShareHighTempLabel` = "High"/"Hámark") — added to both language blocks of `translations.common.js`. Real-browser export (`10-revision2-rain-exported.png`) shows the fixed context line verbatim: `"Thingvellir Test Site · Dagsspá 13.09.2026 · Lítil rigning · Hámark 10°C"`.

## 3. Full renderer geometry — fixed (Ripley Round 1 finding #2)

**Root cause confirmed via Ripley's own preserved repro** (`outputs/ticket-410-weather-voice-share-evidence/weatherVoiceShare.review-repro.test.js`, copied to `src/lib/_review-repro.test.js`, run, confirmed **failing** against the pre-fix code exactly as Ripley described, then deleted after confirming): `fitCommentText` accepted a wrapped result purely by line COUNT — a single unbroken 100-character token produced one "line" that was never checked against `maxWidth`, so it was reported as "fitting" at the 64px start size despite being far too wide. Separately, the context line was drawn on one fixed, unmeasured line at a position (`textBlockTop + lines*lineHeight + 36`) that could land inside the fixed branding block's own `y` range once 5 comment lines were accepted.

**Fix, two parts:**
1. `linesFitWidth(lines, measureWidth, maxWidth)` — every wrapped line's own measured width is now checked, not just the count. Both `fitCommentText` and the new `fitContextText` use it. Ripley's preserved repro now **passes** (re-run after the fix, confirmed).
2. `fitShareLayout({commentText, contextText, measureWidthAtSize, maxWidth, availableHeight})` — a real reserved-height layout solver: fits the comment first (largest size that fits both width and line-count), computes its actual pixel height, and fits the context (which now wraps/shrinks like the comment, with its own floor/ceiling) within whatever height remains under a fixed `availableHeight` budget that sits strictly above the branding block. If the context can't fit at the current comment size, the comment is shrunk further (freeing room) before ever failing — this is what correctly handles a long real campsite name (verified in real-browser evidence, `12-revision2-long-site-name-exported.png`: a 78-character site name wraps to two lines with zero clipping and zero branding overlap) without merely raising the line limit or hiding overflow.

**New tests:** `linesFitWidth`, `fitContextText` (long-name wrapping, height-budget rejection, unbroken-token rejection), `fitShareLayout` (short content fits large, combined height never exceeds budget even for the longest real IS comment, shrinks the comment before failing, returns `null` rather than overlapping branding when nothing fits) — 15 new tests in `weatherVoiceShareImage.test.js`. **Real-canvas exports covering all four explicitly-requested cases:** long real campsite name (`12-revision2-long-site-name-exported.png`), a 4-line comment (`revision2-four-to-five-lines.png`, verified no branding overlap), an unfit unbreakable token under real font metrics (`revision2-unbroken-token` in `results-renderer.json`, rejected with the exact documented error), and the original synthetic-too-long-message case (still correctly rejected under the new layout logic).

## 4. Frozen opening snapshot — fixed (Ripley Round 1 finding #3)

**Root cause confirmed:** `WeatherVoiceCard.jsx` stored only `shareSnapshot?.episodeKey` at open time and passed the **live** `shareSnapshot` prop straight to the dialog. `useWeatherVoice.js`'s `shareSnapshot` `useMemo` depends on (among other things) `site` and `todayRow` object references — a same-episode re-render that rebuilds either (e.g. a forecast refetch producing a structurally-identical but referentially-different `rows` array) produces a **new** `shareSnapshot` object with the same `episodeKey`. Since the dialog's own image-generation effect depends on `[snapshot]` (object identity), this new-but-equivalent object silently restarted image generation and could replace the open preview's content mid-session — contrary to the promised frozen snapshot.

**Fix:** `WeatherVoiceCard.jsx` now holds `openedShareSnapshot` in React state, captured **once** at the moment the share button is clicked (`setOpenedShareSnapshot(shareSnapshot)`), and passes that frozen state value — never the live prop — to `<WeatherVoiceShareDialog>`. A separate `useEffect` still watches the **live** `shareSnapshot` prop against the frozen `openedShareSnapshot.episodeKey` to decide genuine invalidation (a real episode change, or the prop becoming `null`/ineligible) — this is a key-STRING comparison, not an object-identity comparison, so unrelated object-identity churn for the same episode never triggers it, while a genuine key divergence still closes the dialog correctly.

**New tests (`WeatherVoiceCard.test.jsx`):** a same-episode object rebuild (new `shareSnapshot` object, same `episodeKey`, different `tmax`) does NOT replace the open preview's frozen content (asserted via a `data-tmax` attribute on the mocked dialog); the same immunity holds for a **non-good/excellent condition** (`cold`), per approved-prompt-v2.md §4's explicit "include object-identity churn for at least one non-good/excellent condition"; a genuine episode-key change still closes the dialog correctly even after surviving prior object-identity churn. 3 new tests, all passing.

## 5. Dialog and method guards — fixed (Ripley Round 1 finding #4)

**Native availability** now requires BOTH `typeof navigator.share === "function"` AND `typeof navigator.canShare === "function" && navigator.canShare({files})` — previously only `canShare` was checked. Verified by 3 new tests: native button hidden when only `canShare` exists, hidden when only `share` exists, shown only when both are genuinely present.

**Rapid-repeat download suppression root cause confirmed:** the download handler is fully synchronous, and the pre-existing guard read/wrote `busyMethod` **React state**. Two rapid invocations within the same script tick both read the same pre-update `busyMethod` closure value (React batches the state update before either render reflects the first click), so a purely-synchronous handler could in principle run twice before the UI's `disabled` attribute ever reflected the first click. **Fix:** a `attemptInFlightRef` — a plain ref, mutated synchronously and checked first, immune to React's render/batching timing. For the download path specifically, the release is **bounded to the next microtask** (`Promise.resolve().then(...)`), not the same synchronous tick as the click — this is what actually suppresses a genuine rapid repeat click while still allowing a later, deliberate retry once that tick resolves. Verified by a new test that fires two `fireEvent.click()` calls back to back synchronously and confirms only one real attempt (one `<a>` click, one analytics event), then awaits the bounded release and confirms a later click IS a new attempt (two total).

**Download exceptions** are now caught (`try/catch` around the DOM manipulation) and surface the same "share_error" notice used elsewhere — no uncaught error, no success claim.

**Viewport-height bounding:** the dialog panel now has `max-h-[90vh] overflow-y-auto` — bounded to the viewport with its own internal scroll, no layout redesign otherwise. Verified in real-browser evidence at a short mobile-landscape viewport (700×320): the Save button starts below the fold but is confirmed reachable via the dialog's own scroll (`shortLandscapeScenario` in `results-revision2.json`, plus a before/after screenshot pair, `13-.../14-revision2-short-landscape-scrolled-to-save.png`).

**Focus behavior through unrelated parent rerenders** — root cause confirmed: `WeatherVoiceCard.jsx`'s `closeShareDialog` was a plain function declared in the component body, recreated with a new identity on every render; since the dialog's focus-trap effect depends on `[onClose]`, an unrelated parent rerender would re-run that effect, snapping focus back to the dialog's first control regardless of where the user had actually tabbed to. **Fix:** `closeShareDialog` is now wrapped in `useCallback(..., [])` in `WeatherVoiceCard.jsx`, giving it a stable identity across renders. Verified by a new Dialog-level test: tab focus to the second control, rerender with the identical `snapshot`/`onClose` references (simulating an unrelated parent rerender), confirm focus was NOT reset.
