## 1. Baseline reproduction (hypothesis vs. reproduced)

Ripley/Jonesy's **hypothesis** (prompt-review.md, J2): the panel has `max-h-[85vh] overflow-hidden` but is not a flex column, and the content div (`overflow-y-auto overscroll-contain`) has no bounded height, so it is a plausible but not-yet-browser-reproduced clipping cause.

| Check | mobile 320×568 | short landscape 667×320 |

Root cause **confirmed, not just inferred**: the content `<div>` has no bounded height of its own (no `flex`/`min-h-0`/`max-height` on it), so the browser sizes it to its natural content height (1289px / 986px). It therefore never develops internal scroll (`clientHeight === scrollHeight`, `scrollTop` never moves). The *outer panel* (`max-h-[85vh] overflow-hidden`) is what actually clips — silently, with no scrollbar anywhere — cutting the footer and most of the advanced content off below the fold with no way to reach it by wheel, touch-equivalent, or keyboard. This reproduced identically whether the advanced disclosure was collapsed or expanded, and at both narrow viewports tested. Desktop (1280×900) did not reproduce the clipping (85vh = 765px comfortably fits the content there), consistent with this being a short/narrow-viewport-specific bug as reported.

## 4. Layout / focus / lock contract implemented

**Layout (J2).** Panel: `flex flex-col`, `max-h-[85vh] max-h-[85dvh]!` (the trailing `!` is deliberate — confirmed in the built `dist` CSS that Tailwind v4 emits the `dvh` utility *before* the `vh` utility in its own internal ordering regardless of source order, so without `!important` the later `vh` rule would win even in `dvh`-capable browsers; `!important` forces the `dvh` rule to win when supported, and is simply dropped as an invalid declaration — falling back to the plain `vh` rule — in browsers that don't parse `dvh`). Header and footer rows: `shrink-0`. Content: `min-h-0 flex-1 overflow-y-auto overscroll-contain` (unchanged `overscroll-contain`, nested table's own horizontal scroll untouched).

**Dialog semantics (J3/J4).** Panel: `role="dialog"`, `aria-modal="true"`, `aria-labelledby` → `useId()`-generated id on the title element. The existing `aria-label="Close modal"` string and the `document.body`-child portal are byte-for-byte unchanged (the #441 canonical-tone helper and its `queryByLabelText` depend on both). Backdrop changed from a focusable `<button>` to a non-focusable `<div onClick={onClose}>` so it is never a tab stop and never a second "Close" control; click-to-close behavior is unchanged.

**Focus lifecycle (J5–J8).** A single derived `isRendered = open && !!candidate` flag now gates every lifecycle effect (previously keyed on `open` alone, which could lock the body / add listeners with nothing visibly rendered when `candidate` was null). `onClose` is held in a ref updated every render (no-deps effect), so a new inline `onClose` identity from the card on every render never re-triggers focus capture/initial-focus/trap. One merged `window` `keydown` listener (unchanged from the existing single-listener pattern) handles both Escape (exactly once) and Tab/Shift+Tab containment, recomputing the focusable set from `panelRef` at each keydown (so the advanced-disclosure toggle changing the set is handled correctly), re-entering at first/last when `document.activeElement` is outside the known set. Initial focus lands on the content/scroll region itself (`tabIndex={-1}`, `ref={contentRef}`), which is *inside* the scroller, so ArrowDown/PageDown works immediately after opening without an extra click — satisfying J6. Body lock sets/restores the exact prior inline `overflow`/`paddingRight` values (including non-empty ones), scoped to `isRendered`. On cleanup, focus returns to whatever had it before open (`previouslyFocusedRef`), via `focus({ preventScroll: true })`, only if that element is still attached — never throws if the opener is gone.

### K1 — real defect, now fixed (modal-only)

**What Jonesy found, re-derived from this round's own data.** `RoutePlannerDetailsModal.jsx`'s Tab handler had one check: `activeIndex === -1` (focus not matching any element in `FOCUSABLE_SELECTOR`) → treat as "outside the dialog" → `preventDefault()` + jump to `first`/`last`. This conflated two different things: focus genuinely outside the panel, and focus *inside* the panel on an element the browser made keyboard-focusable that simply isn't in our selector list — specifically, Chromium gives a scrollable container with no focusable children of its own (the `overflow-x-auto` wrappers around `RouteCompareTable`'s table and the advanced score-breakdown table) a native Tab stop, with no `tabindex` attribute at all, so it can never appear in `FOCUSABLE_SELECTOR`. Landing on one of those during Tab triggered the "outside" branch and bounced focus straight back to the header close button, so a keyboard user could never reach "Show scoring details" or the footer Close button at the primary viewport this ticket is about (320px wide, where that container's width forces it to actually scroll and thus actually become a stop).

**Fix** (`RoutePlannerDetailsModal.jsx`, the Tab branch inside the same merged keydown handler; no other part of the handler touched): replaced the `activeIndex === -1` check with `!panel.contains(active)` for the "truly outside, re-enter at edge" case, and narrowed interception to the two real boundaries only (`active === first && shiftKey` → wrap to last; `active === last && !shiftKey` → wrap to first). Everything else — a listed control in the middle, *or* a native scroll-container stop not in the list — now falls through with no `preventDefault()` and no forced `.focus()` call, letting the browser's own native Tab/Shift+Tab traversal carry focus through those stops exactly as it already does for any other page. `first`/`last` (and therefore both wrap targets) are unchanged — the header close button and the footer close button, confirmed structurally to be the true first/last tabbable elements in the panel in every state (nothing tabbable exists before the header or after the footer).

**Tests (jsdom, `RoutePlannerDetailsModal.a11y.test.jsx`).** Two pre-existing tests in this file asserted the *old, wrong* behavior directly: "Tab/Shift+Tab re-enters at first/last when focus is on the scroll region" — the scroll region is exactly the in-panel-but-unlisted case that caused K1, so these tests encoded the bug's premise. Corrected: retargeted to use a genuinely external element (`document.body`-appended button, outside the panel) for the "re-enters at edge" assertion, which is what that behavior is actually for. Two new tests added in their place, asserting the opposite for the in-panel-but-unlisted case (using the scroll region itself, a real `tabIndex={-1}` in-panel element absent from `FOCUSABLE_SELECTOR` — jsdom cannot create a real implicitly-focusable scroll container, so this is a faithful stand-in for the one property the handler decision actually depends on): `fireEvent.keyDown` returns `true` (not default-prevented) and focus does not move, in both directions. **Mutation-tested**: temporarily reinstated the exact old `activeIndex === -1` branch, ran only these two new tests — both failed red for the right reason (`expected false to be true`, i.e. the event *was* being prevented) — then reverted and confirmed green again (37/37 in this file, byte-for-byte diff confirmed the revert matched the fix exactly).

### K2 — harness now asserts the sequence, not just logs it

v2's `walkTabOrder` only collected `document.activeElement` into `measurements.json` with no `record()` call, so the 60/60 in v2 could not fail on a keyboard-reachability regression — which is exactly how K1 slipped through undetected into a "PASS" report. Fixed by construction of the K1 work above: every named Tab check (reaches-toggle, reaches-footer-close, reaches-in-DOM-order, wraps-to-first, stays-in-dialog, ×2 directions ×2 states ×2 viewports = 20 new named checks per run) now goes through the same `record()`/`results.json` mechanism as every other check in this harness, so a future regression in either direction would show up as a named, specific `FAIL` line the same way the expected-red run did here.

### Report correction (v2's B7 paragraph was itself wrong)

v2's B7 disposition said: *"in this Chromium build the horizontally-scrollable table container did **not** become its own native tab stop ... the recorded order matched the JS-computed focusable list exactly in this environment."* **This is false and is retracted.** Jonesy's re-check correctly read v2's own saved `measurements.json` and found the opposite: the container *did* become a native stop at mobile320 (both states) and at shortLandscape expanded, and the recorded order did *not* match the focusable list — that mismatch is the entire K1 defect. The error in v2 was: the tab-order data was collected but never checked against anything, so "I didn't see a FAIL" was mistaken for "the order matched," when no check existed that could have failed. This round's named checks exist specifically so that mistake can't recur silently.
