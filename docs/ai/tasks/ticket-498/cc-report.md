## Real bugs found and fixed this round (not hypothetical — each caught by a failing test or a live owner-run check)

1. **`ntfy_client.publish()` had no `port` parameter** — hardcoded
   443/80, so the local test server's actual ephemeral port was never
   reachable; three tests failed on first run with a silently-wrong
   connection target. Added `port: Optional[int] = None` (defaults to
   443/80 for real ntfy.sh use), threaded through `dispatch.py` and
   `config.py`'s `ntfy.port` key.
2. **`ntfy_client.publish()` leaked the socket on any transport
   exception** (`conn.close()` only ran on the success path). Fixed
   with a `finally` block.
3. **`state._FileLock` only caught `FileExistsError`** on the
   "already locked, retry" path; Windows can raise `PermissionError`
   instead when multiple threads race `O_CREAT|O_EXCL` on the same
   path, which crashed a worker thread in the 20-thread concurrency
   test (visible as an unhandled exception even though the test's own
   assertions still passed by luck). Fixed by catching both.
4. **`apply_config_patch.plan_codex()`'s own public return value
   carried the real secret-adjacent old-`notify` value** under a
   leading-underscore key (`_chain_setx_command_real`) — the
   underscore convention wasn't enough; anyone calling `plan_codex()`
   directly (e.g. a future caller that just prints the dict) would
   leak it. Refactored so the real value never enters any function
   `plan_codex` can return; only `apply_codex`'s own internal path
   ever sees it, and only via an injected `run_setx` callable.
5. **Windows toast reports success without ever visibly
   rendering, on this machine, for this unregistered script** — a
   live, owner-run test (2026-11-11, see below) found
   `ToastNotificationManager.Show()` returns `TOAST_OK` with no
   exception while the owner saw nothing, a known Windows behavior
   for an unrecognized AppUserModelID. The balloon-tip fallback WAS
   visibly confirmed — but only after fixing a second, related bug:
   the balloon script only slept 300ms before exiting, tearing down
   its own `NotifyIcon` (and the balloon with it) almost immediately.
   Fixed by (a) defaulting to balloon-first (`prefer_toast=False`,
   new parameter) since toast's own "success" isn't trustworthy
   without AUMID registration, and (b) keeping the balloon process
   alive for its full requested display duration (4s) instead of
   300ms. Re-tested live after the fix — see below.

### RE1/CG2/CG3/CG5 — Codex self-chain recursion — **FIXED (the high-severity finding)**

Confirmed the exact bug Jonesy's own sandbox reproduced: `apply_codex`
was not idempotent. A second `apply` on an already-patched
`config.toml` read the CURRENT `notify` value — now the wrapper
(`cli_codex.py`) itself — as "the old command to chain to," and
persisted THAT as the chain value, while still returning `applied:
true`. With that value persisted, a single real notify firing would
make `cli_codex.py` chain to itself indefinitely; Jonesy's own sandbox
measured ~60–76 self-sustaining orphaned processes (`os._exit` leaves
children running) before a manual `pkill`.

Fixed with one new shared module, `wrapper_detect.py`
(`is_wrapper_argv()`): normalizes each `notify`-array element
(`\`→`/`, lowercase, strip quotes) and flags it if its basename is
`cli_codex.py` *or* it contains that string anywhere (covering a
single shell-wrapped element like `cmd /c "...\cli_codex.py"`) — and
is **fail-closed**: a non-list, empty list, non-string element, or
empty/whitespace string is also flagged, never treated as safe.
Documented, accepted false positive: an unrelated command whose text
happens to contain `cli_codex.py` is also flagged (the safe
direction). This one helper is now used identically by all three
surfaces:

- **`apply_config_patch.py`** (CG2): `_compute_codex_patch` checks the
  CURRENT `notify` value before computing any diff; if flagged,
  returns `{"already_patched": True, "diff": "", "no_op": True, ...}`.

  reason: already_patched`, **zero side effects** (no persist call,
  no backup, no write) — even with `--apply`. `plan_codex` reports
  the same thing for a dry-run. **CG5(a)** additionally: before
  persisting, reads whatever is CURRENTLY persisted (via

### RF2/PS1 — `real_read_back_chain`, CG5(a), and test hermeticity — **FIXED**

Three related gaps, all now fixed:

**(a) Test hermeticity.** The Codex-chain-guard round's own
`test_chain_persisted_state_is_reported_without_the_value` called the
